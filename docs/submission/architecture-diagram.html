LifeGrid

LifeGrid plans household stuff — like a family trip — by splitting the work across several small AI agents instead of one AI trying to do everything itself.

How it works, in plain terms

The pattern, and why

Instead of one AI model freely deciding what to do next, we wrote the steps as a fixed sequence: check for anything unsafe first, then do four pieces of research at once, then check the budget, then write up the plan. Each step is a separate, smaller AI call. We fixed the order on purpose — if the AI were choosing its own next step, a cleverly worded request could talk it into skipping the safety check. A fixed sequence can't be talked out of a step that isn't there to skip. And if the safety check does find something, the whole run stops right there — every later step checks for that before doing any work, so a blocked threat actually halts the pipeline instead of just being logged while everything else runs anyway.

How a request moves through the system

You type a goal and a budget in the browser. That goes to our server, which starts the agents and streams back what each one is doing as it happens, instead of making you wait for a final answer. Along the way, agents look up things you've told it before — like "no early flights" — from a small database. Before anything that would spend money over $100, or book travel at all, it stops and asks you to approve it first.

What Google technology we're using

Gemini (via Vertex AI) does the actual thinking for each agent. Google ADK is the framework that runs the agents in sequence and in parallel. Cloud Run hosts the app. Firestore is the database that remembers your preferences between visits. Cloud Trace records what each agent did, for debugging. And if you sign in with Google, it reads your real Google Calendar (view-only) instead of guessing your schedule.

What we'd add for a real version

Today, flight, hotel, activity, and gear results are realistic sample data, not real bookings — only the calendar check is hooked up to something real. Next would be connecting real flight/hotel search, a couple more safety checks we haven't built yet, and making sure a request doesn't get lost if the server restarts partway through.

What's actually built vs. still in progress

The hackathon track asks for seven specific capabilities. Here's the honest status of each — nothing below is aspirational.

Agent directory
A list of all 7 agents and what each one is allowed to do, viewable live in the app.
Long-running tasks
Runs today, but a run is still tied to one open connection rather than able to survive a restart.
Memory of your preferences
Saved for real in a Google Cloud database once deployed; kept in memory only during local testing.
Permission checks per agent
Every agent can only use the tools it's been given permission for — anything else is blocked automatically.
Spend/booking approval
One shared rule, checked the same way everywhere: over $100, or any travel booking, needs your OK first.
Security scanning
Catches attempts to manipulate the AI through your input — including ones hidden inside a URL — and a detected threat genuinely stops the rest of the run, not just a warning. Doesn't yet check tool results or catch leaked personal data.
Activity monitoring
A live log you can watch as it happens, plus a technical trace of every step saved to Google Cloud.

Multi-agent pipeline

The steps always run in the same order — the AI can't decide to skip the security check, because it isn't a choice it gets to make.
